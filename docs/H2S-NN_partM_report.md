## M7 — Link-prediction protocol (J5)

**Done.**
- New `src/data/hgb_lp_negatives.py`, a port of HGB's `LP/benchmark/scripts/data_loader.py` (THUDM/HGB master, read 2026-11-12 through a fetch agent that returned the code text; byte-exactness of that copy is not guaranteed, the semantics below were checked against it):
  - `hgb_test_negatives` = `get_test_neigh`: binary adjacency `A` of every train, validation and test fact; candidate `(h, t)` iff `(A·A)[h, t] > 0`, `A[h, t] = 0`, `h ≠ t`, `t` of the tail type; heads ascending; `random.Random(1).choices(candidates, k = #test positives of h)`, candidates ascending (the order of HGB's canonical CSR `nonzero()`); **a head without candidates gets no negative**. Only the rows of the test heads and the columns of the tail type of `A·A` are formed (same entries, less memory).
  - `hgb_valid_negatives` = `get_valid_neg`: one uniform tail of the tail type per validation positive, in order, known positives not excluded (HGB does not exclude them). Seed `acm_split_seed + 101 + rel_id` (as before).
  - **Deviation from HGB's literal code (card/spec wording followed):** HGB adds validation facts to `A` in their stored orientation only; the card and spec say "symmetric train + valid + test adjacency", so every fact enters both orientations here. On HGB's own data the difference is usually hidden by reverse relations; on our derived tasks the reverse copy of a validation fact is removed from the message graph, so the two readings can differ. Listed for the author.
- Loader (`link_prediction_dataset.py`): the random fallback (`_sample_hgb_two_hop_negatives(allow_random_fallback=True)` and `_sample_random_tail_negatives`, formerly `:720, :751`), the random branch for tasks without a 2-hop type path (`_sample_hgb_eval_negatives`) and their helpers are removed; test negatives come from `hgb_test_negatives` (AmazonBook branch too), validation negatives from `hgb_valid_negatives`. `PreparedLinkPredData` gains `test_heads_without_negatives` and `test_positives_without_negatives`. HGB's official `_ini` test files are still used when present (none is on disk).
- Negative files, written once per task: new `scripts/lp/write_hgb_negatives.py` → `data/LP/<task>/hgb_negatives/{test_neg_rel<r>.npy, meta.json}` (raw HGB ids; md5 of the test positives the file was drawn for, counts, heads without candidates, md5 of the input files). The loader reads the file when present and raises if it was written for other test positives, so H2S-NN and every baseline bundle (which go through the same loader) see the same negatives. Validation negatives are drawn by the loader (cheap, deterministic, seed recorded). The files are under the git-ignored `data/`; their summaries are in `partM_evidence/m7_write_hgb_negatives_output.txt`.
- Training (`LinkPredictionTrainer._train_epoch`, new `data.link_batch_size = 8192`): each epoch shuffles the training positives into batches of 8,192 with their share of the epoch's 1:1 negatives; one optimizer step per batch and, for H2S-NN, one solve on the whole message graph per step (the epoch's WISP draw is shared by its batches). Why (DERIVED from the schemas): in DBLP an author's only neighbours are papers, whose neighbours are authors, terms and venues, so no paper is two hops from an author; in IMDB a movie's neighbours are directors, actors and keywords, whose neighbours are movies only. HGB's rule therefore gives these two test sets **no negatives at all**: test ROC-AUC is undefined and test MRR is 1 for every method. In ACM a paper reaches authors in two hops only through a cited paper, so papers without a training citation get none. This is the structural fact the Part J report already noted for HeaRT's common-neighbour heuristic. Not a stop condition of the card (the implementation follows the decided rule exactly), but it makes two of the six tasks unusable for test metrics: **first item under "Decisions for the author"**.
