## Z-3 §6 Schema read-out and coverage (analysis of the main runs; not a claim)
**Insert after the Ablation-table bullet:**
> - **Schema read-out and coverage (1.18; analysis of the main runs, not a claim; uses the read-outs of §3.2).** For every node-classification dataset and seed (0–4) of the main table, on the best checkpoint and its fixed evaluation draw (base seed): (i) **coverage** `c_σ` = share of `Σ m_f` over the pairs of sub-path schema σ (i.e. `I_σ` with every `w_f = 1`): how often WISP's draw contains σ; (ii) **learned share** `I_σ` (§3.2, with the learned `w_f`); (iii) **ratio** `ρ_σ = I_σ / c_σ` (1 when `g` is constant, > 1 when the learned weights favour σ beyond its sampling frequency) and the mean `g(ξ_f)` over cells containing σ. Reported: for each listed meta-path of Z-2(a), `c_σ`, `I_σ`, `ρ_σ` per seed; the top ten length-2 sub-path schemas by `I_σ`; the number of distinct sub-path schemas drawn; Kendall τ of the `I_σ` rankings between seeds (C2b). Datasets without a list report the top ten and τ only. **Reading fixed now:** the paper says "the learned weights favour the literature's meta-path σ" only if `ρ_σ > 1` on 5 of 5 seeds; otherwise the values are reported with no statement about selection. No significance test (5 seeds; descriptive). `ΔL_σ` is not reported (its implementation, `src/analysis/wisp_readouts.delta_loss`, uses the v2 operator).
> **Requirement for the server runs:** every seed run of the main table keeps its best checkpoint and resolved configuration; the evaluation draw is rebuilt from the base seed and must reproduce the cells and `w_f` of the end of training exactly (tested before the runs).

## Z-4 §6 Link prediction, Split — the validation carve and HGB's (Part N-fix F1; author decision (a), 2026-11-12)
**Old:** `Every task has a fixed validation file that the loader reads; it lists only the target relation (1.9 F13), so non-target relations stay complete in every task's message graph.`
**New:** `Every task has a fixed validation file that the loader reads; it lists only the target relation (1.9 F13), so non-target relations stay complete in every task's message graph. This differs from HGB's loader in three stated points (1.18; checked against HGB's code, `LP/benchmark/scripts/data_loader.py:44-73`, commit `ca6fd5b`, Part N-fix F1): (i) HGB carves validation from `link.dat` at every load with Python's global generator, which its runner never seeds, so HGB has no fixed validation set; ours is drawn once, with the same probability (10 %) and the same first-fact-of-a-head rule, and written to the file, so every method and every seed sees the same validation facts; (ii) HGB carves every relation, ours only the target relation (F13: the message graph keeps every non-target fact, as in the derived tasks); (iii) HGB's carve may leave a relation's validation empty, ours keeps at least one fact. Replaying HGB's rule over our facts reproduces HGB's validation set exactly (tested), so fact order and rule agree and only the draw differs.`
